## 1. High-Level Overview

**JDBC (Java Database Connectivity)** is a standard **Java API** that defines how a client may access a database. It provides a consistent way for Java applications to interact with various **Relational Databases** (like MySQL, PostgreSQL, Oracle, etc.) without needing to write database-specific code for every different vendor.

At its core, JDBC acts as an **abstraction layer** between your Java application and the underlying **database engine**.

## 2. JDBC Architecture & Interfaces

The JDBC architecture is built on a **two-tier model** consisting of the **JDBC API** and the **JDBC Driver API**.

### 2.1 The Architecture Layers

1.  **The Java Application:** The top layer where your business logic resides. It calls the **JDBC API** to send **SQL statements** and retrieve results.
2.  **The JDBC API:** A set of standard **interfaces** (part of `java.sql` and `javax.sql`) that provide a uniform way to interact with any database.
3.  **The JDBC Driver Manager:** The "traffic controller." It manages the various **database drivers** and matches **connection requests** from the application to the correct driver.
4.  **The JDBC Driver:** The **implementation layer**. Each database vendor provides its own driver that "speaks" the specific **network protocol** of that database.

### 2.2 Core Interfaces

| Interface | Responsibility |
| :--- | :--- |
| **`Connection`** | Represents a physical **session** with a specific database. Used to manage **transactions** and create statements. |
| **`Statement`** | Used to execute **static SQL queries** against the database. |
| **`PreparedStatement`** | A sub-interface of `Statement` used to execute **parameterized**, **pre-compiled** SQL queries. |
| **`CallableStatement`** | A sub-interface used to execute **stored procedures** defined within the database. |
| **`ResultSet`** | A **table of data** representing a database result set, which is generated by executing a query. |
| **`DriverManager`** | The **management class** used to register drivers and establish connections. |

## 3. The Driver Ecosystem

To connect to a database, you cannot simply use the API; you need a specific implementation (the **Driver**) that translates **JDBC calls** into the database's native language.

### 3.1 Driver Types & Registration

**JDBC drivers** are categorized into four types based on how they interact with the database.

| Type | Name | Description | Pros/Cons |
| :--- | :--- | :--- | :--- |
| **Type 1** | **JDBC-ODBC Bridge** | Translates JDBC calls into **ODBC** calls. | **Cons:** Slow, requires **ODBC installation** on the client machine. (Deprecated) |
| **Type 2** | **Native-API Driver** | Uses **client-side libraries** (C/C++) of the specific database. | **Pros:** Faster than Type 1. <br> **Cons:** Requires **database-specific software** installed on the client. |
| **Type 3** | **Network Protocol Driver** | Sends requests to a **middleware server**, which then communicates with the database. | **Pros:** Highly flexible; no client-side DB libraries needed. <br> **Cons:** Adds **network latency** via middleware. |
| **Type 4** | **Thin Driver (Pure Java)** | Converts JDBC calls directly into the **network protocol** used by the database. | **Pros:** High performance; no client-side installation required; written in **pure Java**. <br> **Cons:** Driver is specific to one database. |

> [!TIP]
> In modern development, **Type 4 (Thin Drivers)** are the industry standard due to their **portability** and **performance**.

**Registration:** In older versions of JDBC, you had to manually register a driver using `Class.forName("com.mysql.cj.jdbc.Driver")`. In modern **JDBC 4.0+**, drivers are automatically discovered via the **Service Provider Mechanism**, provided the **driver JAR** is on your **classpath**.

### 3.2 Setting Up the Database Driver

To use a driver in your project, follow these two steps:

1.  **Add the Dependency:** You must add the **vendor-specific JAR file** to your project's **classpath**. If using **Maven**, add the dependency to your `pom.xml`:
    ```xml
    <!-- Example for MySQL -->
    <dependency>
        <groupId>com.mysql</groupId>
        <artifactId>mysql-connector-j</artifactId>
        <version>8.0.33</version>
    </dependency>
    ```
2.  **Establish Connection:** Use the **`DriverManager`** to create a connection using a **Connection URL**.
    ```java
    String url = "jdbc:mysql://localhost:3306/my_database";
    String user = "root";
    String password = "password";
    Connection conn = DriverManager.getConnection(url, user, password);
    ```

## 4. Implementation & Development

### 4.1 Setting Up the Utility Class

To adhere to **DRY (Don't Repeat Yourself)** principles, you should never write connection logic inside your business classes. Instead, create a **Database Utility Class**.

**Standard Utility Pattern:**
```java
public class DBUtil {
    private static final String URL = "jdbc:mysql://localhost:3306/db";
    private static final String USER = "root";
    private static final String PASS = "secret";

    // Method to provide a fresh connection
    public static Connection getConnection() throws SQLException {
        return DriverManager.getConnection(URL, USER, PASS);
    }
}
```

## 4.2 Statement Types: Simple vs. Prepared

There are two primary ways to execute **SQL** in JDBC. Choosing the wrong one can lead to **performance issues** and **security vulnerabilities**.

| Feature | `Statement` | `PreparedStatement` |
| :--- | :--- | :--- |
| **Compilation** | Compiled by the DB *every time* it is run. | **Pre-compiled** by the DB *once*. |
| **Parameters** | Values must be **hard-coded** into the string. | Uses **`?` placeholders** for dynamic values. |
| **Performance** | Slower for **repeated queries**. | Much faster for **repeated queries** (reuses **execution plan**). |
| **Security** | **Vulnerable** to **SQL Injection**. | **Secure** (protects against injection). |

**Simple Statement Example:**
```java
Statement stmt = conn.createStatement();
// Dangerous: Concatenating strings
String query = "SELECT * FROM users WHERE id = " + userId;
ResultSet rs = stmt.executeQuery(query);
```

**Prepared Statement Example:**
```java
String query = "SELECT * FROM users WHERE id = ?";
PreparedStatement pstmt = conn.prepareStatement(query);
pstmt.setInt(1, userId); // Binds the value to the first '?'
ResultSet rs = pstmt.executeQuery();
```

### 4.3 The Security Threat: SQL Injection

**SQL Injection** is an attack where an attacker inserts **malicious SQL code** into an input field, tricking the database into executing unintended commands.

**How it happens (with `Statement`):**
Imagine a login query: `SELECT * FROM users WHERE username = '` + input + `' AND password = '` + pass + `'`.
If an attacker enters `' OR '1'='1` as the username, the resulting SQL becomes:
`SELECT * FROM users WHERE username = '' OR '1'='1' AND password = '...'`

Because `'1'='1'` is always true, the attacker **bypasses authentication** entirely.

> [!WARNING]
> **NEVER** use `Statement` with **concatenated user input**. **ALWAYS** use `PreparedStatement` to automatically **sanitize inputs** via **parameter binding**.

## 4.4 Advanced Execution: Callable Statements

A **`CallableStatement`** is used to call **Stored Procedures**—pre-compiled blocks of SQL code stored on the database server. These are useful for complex, heavy-duty logic that you want to execute close to the data.

**Example: Calling a procedure named `get_user_count`**
```java
CallableStatement cstmt = conn.prepareCall("{call get_user_count(?)}");
cstmt.registerOutParameter(1, Types.INTEGER); // Tells JDBC we expect an INT back
cstmt.execute();
int count = cstmt.getInt(1); // Retrieves the result
```

## 5. Data Retrieval & Navigation

### 5.1 Understanding the ResultSet

When you execute a `SELECT` query, the database returns a **`ResultSet`**. You can think of a `ResultSet` as a **cursor** pointing to a "virtual table" of rows.

*   The **cursor** initially points **before the first row**.
*   You must move the cursor to the first row before you can read any data.

### 5.2 Navigating ResultSet Rows

To move through the data, you use **"iterator" methods**.

**The Standard Loop Pattern:**
```java
ResultSet rs = pstmt.executeQuery();

// .next() moves the cursor to the next row and returns true if a row exists
while (rs.next()) {
    // Retrieve data using column name or index
    int id = rs.getInt("id");
    String name = rs.getString("username");
    System.out.println("User: " + id + " | Name: " + name);
}
```

> [!IMPORTANT]
> **Column Access Nuance:** When retrieving values from a `ResultSet`, you can use either the **Column Name** (e.g., `rs.getString("username")`) or the **Column Index** (e.g., `rs.getString(2)`). Note that **Column Indices are 1-based**, not 0-based.

**Key Retrieval Methods:**
*   `rs.getInt(String colName)` / `rs.getInt(int colIndex)`
*   `rs.getString(String colName)`
*   `rs.getDouble(String colName)`
*   `rs.getDate(String colName)`

**Navigation Modes (ResultSet Types):**
By default, a `ResultSet` is **Forward-Only** (`TYPE_FORWARD_ONLY`). You can only move from row 1 to row 2, etc. If you need to move backward or jump to specific rows, you must create the statement with different types:

| Type | Name | Capability |
| :--- | :--- | :--- |
| `TYPE_FORWARD_ONLY` | **Forward-Only** | Move only forward. |
| `TYPE_SCROLL_INSENSITIVE` | **Scrollable (Insensitive)** | Move forward, backward, or to **absolute rows**. Changes in DB are **not visible**. |
| `TYPE_SCROLL_SENSITIVE` | **Scrollable (Sensitive)** | Move anywhere. **Reflects real-time changes** in the DB. |
